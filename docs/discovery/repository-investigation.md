# Repository and deployed-site investigation

Date: 2026-07-27

## Scope and evidence

This investigation used the public GitHub repository tree and README, the deployed production pages, generated documentation already present in the project, and the confirmed domain decisions. The execution environment could not complete a direct `git clone` and had no authenticated GitHub connector. Therefore file-by-file implementation details that are not exposed by the public pages/README remain marked as unverified rather than guessed.

No production source or dataset was changed during investigation.

## Framework and rendering architecture

- Public repository documentation identifies the framework as Vite with a React interactive application.
- `src/App.jsx` is documented as the main interactive experience.
- `scripts/postbuild.mjs` is documented as generating static research/entity pages, Schema.org metadata, sitemap entries, and static API outputs after the Vite build.
- Vercel serves `dist` and runs `npm run build` under Node.js 22.
- The result is a hybrid static publication: an interactive atlas plus post-build generated, crawlable pages and machine-readable endpoints.

## Route structure

Documented or observed public routes include:

- `/` interactive/home entry
- `/research/` research hub
- `/research/<study>/` generated research pages
- `/poets/` and generated poet pages
- century and metaphor/entity pages generated by the publication pipeline
- `/methodology/`, `/data/`, and `/glossary/`
- `/api/*.json`, `/downloads/*.csv`, `/openapi.json`

The disposable package adds only `/prototype/` and does not replace existing routes.

## Content and data-generation pipeline

The repository README documents this flow:

1. Raw corpus remains at `public/data/poems_with_more_info.tsv`.
2. Python generators create compact JSON research artifacts and CSV audit/download files.
3. The React application consumes analytical JSON for interactive views.
4. `scripts/postbuild.mjs` materializes static research/entity pages, APIs, metadata, and sitemaps into `dist`.
5. SEO/GEO scripts audit generated output.

Known canonical analytical artifacts include `src/data/atlasData.json`, `src/data/attributionResearch.json`, and `src/data/publicQuestionsResearch.json`.

## Visualization layer

- The repository exposes `src/chartOptions.js` as the shared chart-configuration module.
- The exact chart package and the depth of its wrappers could not be verified from the accessible public source view.
- Production pages expose numerical prose and tables, while the interactive atlas is the visualization-heavy surface.
- Accessibility equivalence between every interactive chart and a data table was not observable across all atlas states and must be verified from a local checkout before implementation.

## Reusable components and hotspots

Public architecture documentation points to a small number of high-responsibility files:

- `src/App.jsx`: interactive experience and likely route/view orchestration;
- `src/chartOptions.js`: chart configuration;
- `src/content/siteContent.js`: research copy, FAQ, and glossary;
- `scripts/postbuild.mjs`: many static pages, metadata, API, and sitemap outputs.

These are likely change hotspots and potential shallow-module boundaries. This is an assessment cue, not proof of poor design; local source inspection is required before any refactor.

## Typography, RTL, and mobile

- The deployed pages are Persian and RTL-first.
- Production typography is legible and uses Persian number presentation in public prose.
- Generated pages expose a consistent header, content hierarchy, and footer.
- A mobile-specific behavioral audit could not be completed with the unavailable browser screenshot facility in this environment. The disposable prototype uses logical CSS properties, native controls, visible focus, reduced-motion handling, and mobile breakpoints.

## Accessibility implementation

Observed strengths:

- Generated pages use semantic headings, links, tabular data on the data page, and visible methodological caveats.
- Search on the poet index is represented as a native input.
- The methodology and data routes provide text alternatives to many quantitative claims.

Verification gaps:

- keyboard interaction of atlas tabs, charts, filters, tooltips, and dialogs;
- focus order and focus visibility in all interactive states;
- screen-reader names/descriptions for charts;
- equivalence of chart and table values;
- no-JavaScript behavior of interactive routes;
- contrast and zoom/reflow checks at 200–400%.

## Metadata and structured data

The public repository documents `CITATION.cff`, `codemeta.json`, Schema.org generation, sitemap generation, OpenAPI, static JSON APIs, and OG cards. Generated pages include descriptive titles and citation blocks. A local build should validate that entity/research pages use the most specific suitable types and canonical URLs consistently.

## Test coverage

The public README documents build and SEO audit commands, but the accessible source view did not establish a comprehensive unit/component/browser test suite. Previous project reports emphasize syntax, JSON/CSV integrity, page generation, link audits, and manifest checks. Public behavioral seams for keyboard, URL filters, chart/table equivalence, and data integrity should be added before production implementation.

## Performance risks

Likely bottlenecks to measure rather than assume:

- a large `App.jsx` interactive entry and initial analytical JSON payloads;
- chart-library bundle and eager chart initialization;
- repeated content/data embedded in the SPA and generated static pages;
- web-font loading and OG/static asset volume;
- post-build generation cost as entity pages grow.

The production target should be based on field Core Web Vitals, segmented mobile/desktop, not only local Lighthouse.

## CSV and JSON downloads

The data page currently publishes multiple CSV files and a JSON summary. Repository docs state that Python generators create research CSV/JSON and that post-build copies or exposes them under `/api/` and `/downloads/`. Integrity should be checked by parsing outputs, validating schema/version, and comparing representative values to the same canonical artifact consumed by pages.

## Poet, century, metaphor, and research page generation

Repository docs identify `scripts/postbuild.mjs` as the generator for static research/entity pages. The deployed `/poets/` page lists 67 generated poet entries with counts and a local warning that corpus presence is not literary rank. Research pages follow a repeated pattern: answer, evidence, method/table access, and interpretive limits. Exact generator function boundaries require local source inspection.

## Single source of truth assessment

The architecture intends a generated-data flow, but multiple analytical JSON files, prose constants, chart options, generated HTML, and CSV outputs create an integrity risk unless metric definitions and values share stable identifiers and schemas. The production/source discrepancy below is a concrete reason to add cross-output integrity tests.

## Source/deployment discrepancy

The public repository README describes version 7 with ten research studies and a `/research/public-questions/` output. On 2026-07-27, the deployed homepage and research hub visibly described **nine** studies and did not surface the tenth public-questions study. This may be a stale deployment, a post-build publication mismatch, or a repository/deployment revision mismatch. The root cause was not inferred without a local checkout and deployment logs.

## Investigation conclusion

The next safe production step is not a redesign commit. It is selection of one prototype direction, followed by a complete specification and a local checkout audit of the identified hotspots and public seams.
